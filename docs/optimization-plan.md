# Subagent Governance 优化方案

## 目标

在不替换 Codex 原生 `spawn_agent`、不修改现有第三方 Skill、不引入 MCP 或 Agents SDK 编排层的前提下，把当前插件从可用的 `0.1` 原型提升为长期稳定运行的通用子 Agent 治理组件。真实运行验证发现原生 `spawn_agent` 会在 Hook 前加密任务正文，因此正式可用版本调整为 `0.4.0`，增加独立的可观察治理通道和平台错误对账。

核心指标：

- 治理组件自身故障时，不应让原生子 Agent 不可用。
- 每个受治理任务都能形成完整且可恢复的生命周期。
- 终态验收减少误判，不依赖容易命中的全文关键词。
- AGENTS、Skill、Hook、Schema 不再各自维护相互漂移的协议。
- 开发版、稳定发布源和运行缓存有明确、可验证的发布边界。
- 真实传输不透明时，插件不伪称已读取正文契约，仍能可靠识别显式治理等级。
- provider 失败不会让治理状态长期停留在假 `running`。

## 第零阶段修订：真实传输约束

实跑证据显示，父 Agent 写入的 `message` 在进入 `PreToolUse` 前可能已经变成不透明密文；Hook 能追加治理信封，但不能读取其中的 `【治理等级】`、目标、范围和验收字段。原方案中“所有契约字段都由 PreToolUse 从 message 机械解析”的假设不成立。

修订后的双通道方案：

- 完整自然语言契约继续放在 `message` 中，由子 Agent 解密并执行。
- `task_name` 使用 `sg_<mode>_<semantic_name>` 传递 Hook 可见的治理等级和最小恢复语义。
- 明文调用仍支持完整字段校验；不透明调用记录 `message_visibility=opaque`，不伪造结构化字段已被验证的结论。
- 未带前缀的不透明调用默认 standard，保持第三方和直接 `spawn_agent` 的兼容性。
- `PostToolUse` 观察 `list_agents`，把 `errored` 对账为 `platform_error`；成功 follow-up 和再次启动恢复原任务状态。
- 当前 Codex 的 `spawn_agent` 返回使用 `task_name: /root/...` 表示 canonical task path；运行时必须把该真实字段纳入 Agent→治理任务映射，不能只依赖旧测试中的 `canonical_task_path`。
- 同一任务只允许一次平台错误自动恢复；恢复后再次失败转为 `needs_decision`，不继续消耗请求。

验收：脱敏不透明 payload 能选择显式 strict；无前缀时稳定降级 standard；`list_agents` 中的 `stream disconnected` 不再留下永久 running 记录，重复平台失败也不会形成无限 follow-up 循环。

## 第一阶段：可靠性修复（建议版本 0.1.1）

### 1. 中断生命周期闭环

问题：`interrupt_agent` 被 Hook 匹配和识别，但成功中断后任务仍保持 `running`，父任务可能被 `Stop` Hook 阻止。

改进：

- 为 `interrupt_agent` 增加 `PostToolUse` 处理。
- 成功中断记录为 `interrupted`，从活跃状态集合移除。
- 中断失败保持原状态并记录失败原因。
- 保留任务与 agent 映射供诊断使用。

验收：中断一个运行中子 Agent 后，父任务能够正常结束；失败中断不会错误终止任务。

### 2. 状态存储故障降级

问题：状态文件损坏、权限异常、空间不足或超过上限时，当前 `PreToolUse` 会拒绝所有派发和通信。

改进：

- 把派发契约错误与状态持久化错误分开处理。
- 契约错误继续拒绝；治理存储错误告警并降级放行。
- 损坏状态文件隔离为 `.corrupt-<timestamp>`，重新创建空状态。
- 在诊断输出中报告 `degraded` 和原始错误。

验收：损坏状态文件后仍可调用原生 `spawn_agent`，同时能看到明确治理告警。

### 3. 修复终态状态误判

问题：全文包含英文 `blocked` 就会把已完成任务记录为阻塞，例如 `no blocked items`。

改进：

- 优先解析明确的 `状态:` 或 `Status:` 字段。
- standard 没有明确状态字段且验收通过时默认 `complete`。
- 禁止使用全文子串推断阻塞状态。

验收：否定句、说明文字和文件名中的 `blocked` 不改变任务状态。

### 4. 补充故障回归测试

至少新增：

- 成功/失败中断。
- 损坏、超限、只读状态文件。
- `no blocked items` 等否定表达。
- `auto` 风险词出现在禁止范围或背景中的分类。
- 并发启动与 PostToolUse 映射竞态。

### 5. 清理旧实现残留

当前安装环境仍可能存在指向迁移备份的 `~/.codex/hooks/subagent_policy.py` 符号链接，以及已经不再对应有效 Hook 挂载的历史信任记录。它们目前不参与插件运行，但会让零残留检查失败并混淆后续维护。

改进：

- 发布维护窗口中确认旧脚本没有被 `hooks.json`、`config.toml` 或其他有效配置挂载。
- 当前配置解除挂载后，先把旧脚本路径作为老任务兼容层保留；确认相关任务全部结束且经用户明确授权后再删除链接，不要删除其回滚备份。
- 不手工编辑 Codex-owned Hook 信任哈希，通过受支持的 Hook 管理流程清理由产品负责的状态。
- 重新运行组件 `--inspect`、Hook 列表检查和 Registry validation。

验收：只有七个插件 Hook 生效，旧实现没有挂载；未挂载但为老任务保留的 legacy 路径不会让组件一致性检查失败。

### 6. 保留滚动升级兼容缓存

Codex 已打开任务会继续引用启动时解析出的版本化 Hook 路径。旧版本缓存因此不是可立即清理的 legacy residue；在老任务结束前移动它会导致 `Stop` 等 Hook 找不到脚本。

改进：

- 更新稳定版时保留上一版本的普通目录缓存，不创建符号链接。
- 通过发布包装器在运行 `codex plugin add` 前暂存全部旧缓存，并在命令清理后恢复；不能只依赖操作人员记住“不要删除”。
- 安装检查把这些目录报告为 `retained_compatibility_caches`，与真正的 legacy Hook 挂载分开处理。
- legacy 脚本路径是否存在与是否仍被当前配置挂载分开检查，避免清理动作破坏已打开任务。
- 只有确认引用旧版本的任务全部结束后才清理，并保留可恢复备份。

验收：升级后老任务仍能执行其固定版本 Hook，新任务加载新版本；严格安装检查允许安全的兼容缓存，但拒绝缓存目录中的符号链接或非目录条目。

## 第二阶段：协议与恢复能力收敛（建议版本 0.2.0）

### 1. 单一任务契约来源

建立内部 `TaskContract` 和 `TaskResult` 模型，统一提供：

- 字段解析与规范化。
- light、standard、strict 的机械校验规则。
- Schema 导出或校验。
- 状态文件序列化。
- 诊断展示。

文档必须明确区分“模型软指导”和“Hook 强制规则”。不再让 AGENTS、Skill、Python 常量和 JSON Schema 分别定义不同协议。

### 2. 保存有限恢复上下文

状态记录增加有长度上限的：

- `objective`
- `scope`
- `completion`
- `agent_id`
- `canonical_task_path`
- `last_transition`

不读取不稳定 transcript，不保存完整父线程或敏感工具输出。

验收：上下文压缩后，父 Agent 能识别每个活跃子任务的目标、完成条件和恢复对象，而不只是看到任务 ID。

### 3. 改进 auto 分类

- 区分目标动作、禁止动作和背景说明。
- 记录选择结果及 `mode_reason`。
- 显式 strict 才强制固定终态模板。
- `auto → strict` 强化证据要求，但避免仅因格式不足反复续跑。

## 第三阶段：生命周期、诊断和发布（建议版本 0.3.0）

### 1. 状态清理

- 增加 `SessionEnd` Hook。
- 定期删除过期终态记录，保留有限历史。
- 接近状态大小上限时先清理终态，而不是直接拒绝写入。
- `SessionStart` 补充 `clear` 来源的行为定义。

### 2. 可用诊断

- `--diagnose` 始终输出实际检查的数据根目录。
- 增加 `--data-root` 和机器可读 JSON 状态。
- 输出活跃任务、终态任务、降级状态、协议错误和最后状态转换。
- 安装/卸载逻辑使用已登记的数据路径，而不是依赖 Hook 进程中的临时环境变量。

### 3. 真实 Hook 契约测试

- 保存当前 Codex 版本产生的脱敏 Hook payload fixture。
- 覆盖七类事件和不同工具命名别名。
- 增加源目录、稳定发布源和运行缓存的边界检查。
- CI 跑 Linux；本机发布门禁跑实际 Codex Plugin/Skill validator。

## 明确不做

- 不创建新的 Agent 调度服务。
- 不引入 MCP 作为本地生命周期治理的必需依赖。
- 不要求第三方 Skill 改写成专用协议。
- 不自动执行项目测试、部署或外部系统操作。
- 不把关键词分类描述成安全分类器。

## 发布完成标准

- 所有新增缺陷都有先失败后通过的回归测试。
- Plugin、Skill、Python 编译和完整测试通过。
- 可执行变更完成安全审查。
- 稳定发布源来自干净 Git tag。
- 开发仓库、稳定发布源、运行缓存互不为符号链接。
- 新版本在新 Codex 任务中完成真实派发、终态补充、中断、恢复和父任务结束验证。
