# SG-F08 多 Agent 协调与组级闭环盘点

## 文档状态

- 当前状态：盘点完成；八个功能点及整体文件覆盖、证据边界、跨功能冲突和最终修改方案输入均已确认，不再增加新的功能点。
- 一句话职责：在不替代 Codex 原生 Agent 工具的前提下，把多个独立治理任务组织成具有稳定引用、依赖关系、资源边界、独立恢复能力和组级结果闭环的协调任务组。
- 本文是 SG-F08 的唯一盘点文档；不修改主盘点文档或 SG-F04、SG-F05、SG-F06、SG-F07 独立文档。
- 本轮只记录盘点结论，不修改运行时代码、Schema、Skill、测试、fixture、README、AGENTS.md 或真实 Agent 状态。

## 一、功能边界

### 1. 主要负责

- 建立多个治理任务之间的协调计划、父子关系、依赖边、稳定顺序和组级策略引用。
- 规范批量派发、并发容量、共享资源、批量等待、部分失败、独立恢复、中断传播和结果汇聚之间的组合关系。
- 保存足以跨 `compact`、resume 和网络断流恢复的协调组身份及任务引用，避免一个 Agent 异常导致整批任务重复派发。
- 区分 AI 负责的任务拆分、依赖理由、资源判断和结果汇聚，与脚本负责的 ID、引用、枚举、顺序、完整性及状态记录。

### 2. 明确不负责

- 不重新定义 SG-F01 的单任务治理等级、`TaskContract`、模型、推理强度或上下文策略。
- 不重新实现 SG-F03 的单 Agent 通信参数和原生 `send_message`、`followup_task` 调用。
- 不重新实现 SG-F05 的单任务状态安全、等待巡检、平台对账、恢复上限、中断或 Session 生命周期。
- 不重新定义 SG-F06 的 individual `TaskResult`、`SubagentStop` 验收和单任务父任务闭环。
- 不拥有 SG-F07 的诊断入口、失败分类或输出协议，只提供未来可被诊断消费的协调图和组级事实。
- 不创建后台 scheduler、队列服务、远程协调系统或第二套 Agent 编排平台，不替代原生 `spawn_agent`、`wait_agent`、`list_agents`、`send_message`、`followup_task` 和 `interrupt_agent`。

## 二、候选功能点

1. 协调计划与任务图。
2. 批量派发与并发容量。
3. 父子层级与治理规则传播。
4. 共享资源与写入冲突协调。
5. 协调组状态与会话恢复。
6. 多目标等待与事件路由。
7. 部分失败、独立恢复与中断传播。
8. 结果汇聚与组级闭环。

八个功能点共同描述多个 individual task 的组合关系和组级生命周期，不再把批量展示表格、`child_agents`、并发状态写入测试或诊断输出拆成独立业务功能。

## 三、第 1 项：协调计划与任务图

### 1. 当前情况

当前项目没有独立的协调计划、任务图或协调组协议。多 Agent 任务的拆分、先后关系和并行判断完全由父 Agent 在自然语言中临时完成，随后分别调用原生 `spawn_agent`；治理运行时只能看到一系列彼此独立的单任务派发。

当前已经存在的局部基础如下：

- `SKILL.md` 允许批量并行派发时使用一张用户可见表格，但只要求逐 Agent 展示目标、治理等级、模型、强度、上下文、范围和完成条件；没有批次 ID、任务引用、依赖边、稳定顺序或图级策略。
- SG-F01 的 `TaskContract` 和 `task-contract-v1` Schema 能描述一个任务的目标、范围、完成条件、模型、上下文和 `child_agents=allow|deny`，但没有 `coordination_id`、`parent_task_id`、依赖引用或组级字段。
- `_task_id()` 为每次原生派发生成单独执行身份；相同参数的并发派发不会共用任务 ID，但这些 ID 没有共同的协调组引用。
- `StateStore` 按 session 保存扁平的 `tasks` 和 `agents` 映射，没有协调组、父子图、依赖边、静态计划版本或图完整性记录。
- `auto` 可以因允许下级 Agent 或高风险信号提升治理强度，但该判断只影响单任务 `mode`，不会建立父子任务关系或执行顺序。
- `tests/test_concurrency.py` 只证明 32 个并发 `spawn_agent` 的状态写入不会丢失单任务记录；它不证明这些任务属于同一计划、依赖有序、业务写入无冲突或结果可以汇聚。
- 当前仓库没有 `CoordinationPlan`、协调 Schema、任务图 fixture、循环依赖检查、缺失引用检查或拓扑顺序测试。

因此，现状只能证明“多个单任务可以被并发记录”，不能证明项目已经具备多 Agent 协调计划能力。批量表格、`child_agents` 和并发状态测试都不应被描述成正式任务图协议。

### 2. 与前后文的交接

#### 上游交接

- SG-F01 继续拥有 individual `TaskContract`、治理等级、模型、上下文和单任务完成条件；本项只引用这些单任务契约，不复制或扩张其业务字段。
- SG-F01 已提出确定性契约生成器和短期 `PreparedContractStore` 候选。本项未来应在同一生成阶段形成协调计划及单任务引用，不能要求 Hook 从多次独立 `spawn_agent` 正文中事后猜测任务图。
- SG-F02 继续拥有插件发现、Hook 注册和统一运行时路由；本项只消费已有原生派发事件，不增加后台调度器或新的执行通道。
- 父 Agent 或 AI 负责判断任务是否值得拆分、为什么存在依赖、哪些任务可并行以及业务上应如何汇合；脚本不能根据关键词替代这些判断。

#### 下游交接

- 第 2 项“批量派发与并发容量”消费计划中的任务集合、稳定顺序和依赖就绪关系，决定实际原生派发波次；本项不执行派发。
- 第 3 项“父子层级与治理规则传播”补充嵌套 Agent 的父任务、层级和规则传播；本项只提供稳定图引用，不在此决定下级 Agent 权限细节。
- 第 4 项“共享资源与写入冲突协调”为图节点增加资源与所有权约束；本项不根据文件名或自然语言自动推断冲突。
- 第 5 项“协调组状态与会话恢复”保存计划的运行实例、节点状态和跨会话恢复信息；本项定义的静态计划不能与可变运行状态混成一个平面 `status`。
- 第 6、7 项分别消费任务图决定等待集合、失败影响范围、恢复目标和中断传播边界。
- 第 8 项按任务图和 individual `TaskResult` 引用执行 fan-in 汇聚；本项不生成组级结果或判断业务结论正确性。
- SG-F07 可以读取协调组、节点、依赖和图完整性事实进行诊断，但不拥有任务拆分或调度决策。

#### 跨功能排除

- SG-F04 只负责未来协调协议随稳定版本发布及跨 N/N-1 的格式兼容门禁，不决定协调字段和任务图语义。
- SG-F03 的通信仍面向一个明确 Agent；是否需要通知哪个节点由协调逻辑判断，消息结构和原生投递仍归 SG-F03。
- SG-F05 的文件锁和原子更新可以作为协调状态存储的安全底座，但“写入没有丢记录”不能替代图合法性、派发幂等或业务冲突证明。
- SG-F06 的 individual `TaskResult` 是以后组级汇聚的输入，不应为了多 Agent 汇聚而修改成同时承担任务图和聚合状态。

### 3. 改进建议

建议建立独立、版本化的 `CoordinationPlan` 或等价协调信封，与 individual `TaskContract` 保持引用关系，而不是把所有组级字段直接塞入每个单任务契约。

候选职责分层如下：

#### AI 提供的业务内容

- 整体协调目标及为什么需要多个 Agent。
- 每个任务的业务目标、范围、完成条件及与单任务契约的对应关系。
- 任务之间的依赖理由、并行或串行理由，以及依赖完成后允许继续的业务条件。
- 需要由父 Agent 最终处理的业务汇聚意图；具体组级结果协议留给第 8 项。

#### 脚本生成或机械维护的字段

- 协议版本和唯一 `coordination_id`。
- 每个图节点的稳定 `task_ref`，以及创建 individual `TaskContract` 后的 `task_id` 引用。
- 可选的 `parent_coordination_id` 或 `parent_task_id`；顶层主任务没有治理任务身份时不得伪造父任务 ID。
- 明确的依赖引用、稳定输入顺序、脚本计算的拓扑顺序和计划完整性摘要或哈希。
- 计划创建时间、生成器版本和有界容量字段；最终字段名称与 Schema 在统一方案中决定。

#### 最低机械校验

- `coordination_id`、节点引用和任务引用唯一且格式合法。
- 所有依赖都指向同一计划内存在的节点，不允许自依赖、重复依赖或悬空引用。
- 依赖图无环，并能产生稳定拓扑顺序；同层节点维持明确且可重复的稳定顺序。
- 节点数、依赖边数和业务文本体积有明确上限，错误包含可定位但不敏感的节点引用。
- individual contract 与协调节点之间是一对一稳定引用；不得通过相同目标文本、`task_name` 或派发先后猜测身份。
- 机械校验只确认图结构和引用完整性，不判断任务拆分是否聪明、依赖理由是否充分或业务结果是否正确。

目标链路建议为：

```text
父 Agent 生成业务拆分与依赖判断
  → 确定性生成器创建 CoordinationPlan 和 individual prepared contracts
  → 机械校验任务引用、依赖完整性和无环性
  → 第 2 项按就绪节点调用原生 spawn_agent
  → 第 5 项保存协调运行状态
```

不能让 Hook 根据多个已经发生的派发事后拼接协调图，也不能让协调计划直接执行调度、等待或结果验收。原生 Agent 工具仍是唯一执行通道。

### 4. 可以顺手直接实施的内容

本项没有适合现在孤立修改的运行时代码、Schema、Skill 或测试。

原因如下：

- 直接给 `TaskContract` 增加 `coordination_id` 或依赖字段，会把单任务契约与组级协议混在一起，并提前占用 SG-F01、SG-F05 和后续功能尚未统一的边界。
- 直接给 `StateStore` 增加 `groups` 或图字段，会同时涉及状态版本、迁移、裁剪、SessionStart/End、诊断和 N/N-1 兼容，不能作为低耦合修补。
- 直接扩写批量派发规则会形成只有自然语言承诺、没有生成器、Schema、状态和测试支撑的新协议。
- 直接新增循环依赖测试也需要先确定正式数据结构和生成入口，否则只能测试临时 fixture，无法约束目标实现。
- `tests/test_concurrency.py` 的名称可能让人误以为覆盖业务协调，但它仍是 SG-F05 的有效状态并发回归；本项不直接重命名或移动。

本轮可以直接完成的只有本文记录：确认本项名称、静态计划边界、参数所有权、最低机械校验和与其他功能的交接。

### 5. 必须留待最终统一方案的内容

- `CoordinationPlan` 的最终名称、Schema、协议版本、存储位置和生成入口。
- `coordination_id`、`task_ref`、`task_id`、`parent_task_id`、`parent_coordination_id` 哪些必填，以及顶层父任务没有治理 ID 时的表达方式。
- 依赖边是否只表达“完成后可继续”，还是还需要 `complete`、`blocked`、`needs_decision` 等不同结果条件；该决定必须与第 7、8 项共同设计。
- 静态计划、prepared contract、已派发运行实例和组级状态之间的引用及过期策略。
- 计划修改、节点追加、重试重建和 compact/resume 后的版本、幂等和冲突规则。
- 循环依赖、悬空引用、重复节点、容量超限和计划篡改时是拒绝、降级还是请求决策。
- 协调计划与 StateStore 的版本迁移、SG-F04 N/N-1 兼容门禁及 SG-F07 只读诊断格式。
- 真实 Codex 平台是否提供足够稳定的任务、Agent、父子和 session 身份；仓库单元测试不得替代真实平台证据。

### 6. 不再作为目标的内容

- 不把一张用户可见的批量派发表格当作正式协调计划。
- 不把 `child_agents=allow|deny` 当作父子任务图或规则传播协议。
- 不从相邻 `spawn_agent` 调用、相同 `task_name`、自然语言目标或事件先后自动猜测任务依赖。
- 不把 `tests/test_concurrency.py` 的 32 个并发状态写入描述成任务图、共享资源协调或结果汇聚证明。
- 不让 Hook 自动决定复杂业务任务如何拆分、哪些任务应依赖或最终业务结论是否可以合并。
- 不建立自行执行拓扑图的 scheduler、队列或第二套编排平台。

### 7. 测试与证据

- 当前 `test_auto_promotes_to_strict_when_child_agents_are_allowed` 只证明 `child_agents=allow` 会让 `auto` 选择 strict，不证明实际发生 nested spawn 或建立父子映射。
- 当前 `tests/test_concurrency.py` 只证明同一 session 下 32 个并发派发的状态记录没有丢失，不证明协调图、依赖顺序或业务写冲突安全。
- 当前 Schema 与 `TaskContract` 形状一致性测试只覆盖 individual contract，不包含协调计划。
- 当前没有协调 Schema、图 fixture、循环依赖、悬空引用、稳定拓扑顺序、计划容量、计划幂等或跨 compact/resume 的定向测试。
- 未来实现前应先增加确定性生成、Schema 形状、引用完整性、无环性、稳定排序、非法图拒绝和单任务契约绑定测试；真实多 Agent 派发与父子可见性仍需单独平台验收。

### 8. 本项结论

- “协调计划与任务图”必须保留，是 SG-F08 区别于 SG-F01 单任务契约、SG-F05 单任务生命周期和 SG-F06 单任务结果的首要边界。
- 当前项目没有正式实现该能力；已有批量表格、`child_agents` 和并发状态测试只能作为局部输入，不能证明多 Agent 协调存在。
- 本项应形成独立静态计划并引用 individual contracts；运行状态、资源冲突、等待、恢复和结果汇聚分别交给后续功能点。
- 当前不修改运行时代码、Schema、Skill 或测试，只把目标结构和跨功能约束记录为最终统一方案输入。

## 四、第 2 项：批量派发与并发容量

### 1. 当前情况

当前没有批次级派发入口或并发容量模型。父 Agent 可以按照 Skill 中的用户可见表格说明，连续或并行调用多次原生 `spawn_agent`，但每次调用都会被当作一个独立任务处理；运行时没有批次 ID、波次、并发上限、就绪队列或“已成功节点不可重复派发”的组级记录。

已有的逐次派发链路如下：

- `PreToolUse` 为每个调用生成独立 `task_id`，把单任务契约写入 session 的 `tasks`，初始状态为 `pending`，再将治理信封追加到原生消息。
- `PostToolUse` 独立处理每次 spawn 响应：按 `tool_use_id` 优先绑定，事件 ID 漂移时按 `task_name`/`turn_id` 回退；成功但没有 Agent 身份时仍写成 `running`，形成 `unmapped running`。
- 响应被识别为错误时只把对应任务标为 `failed`，不会回滚或取消同一批其他任务，也不会保存一个批量失败摘要或未派发节点集合。
- `StateStore` 的文件锁和原子替换能够保护并发状态写入；它不负责限制原生 Agent 槽位、不提供排队、不检测平台容量，也不提供批量事务。
- Skill 的批量表格只规定每个 Agent 应展示的目标、治理等级、模型、强度、上下文、范围和完成条件。它是用户沟通格式，不是脚本可读取的批次协议。
- 当前可观察的原生平台并发槽位是运行环境的即时能力，不是仓库稳定参数；项目不能把某次会话的槽位数量硬编码成通用保证。

因此，现状最多能证明“多个独立 spawn 的状态更新不会互相覆盖”。它不能证明：槽位不足时会自动分波、部分派发失败时会保留成功任务、恢复时不会整批重派、依赖未满足的任务不会提前启动，或父任务能取得完整批次进度。

### 2. 与前后文的交接

#### 上游交接

- 第 1 项“协调计划与任务图”提供批次要派发的节点集合、依赖就绪关系和稳定顺序；本项不重新判断业务拆分或依赖理由。
- SG-F01 提供每个节点的 individual `TaskContract`、治理等级、模型、上下文和完整首句；批量表格可以做主对话摘要，但不能替代每个 Agent 的完整 dispatch prompt。
- SG-F02 提供 `PreToolUse`/`PostToolUse` 路由和原生工具边界；本项不增加新的工具名、队列服务或后台派发器。
- 父 Agent 负责根据计划和平台当前可观察情况选择并行或串行调用；插件不能假设自己拥有平台槽位预留权。

#### 下游交接

- 第 3 项消费每个批次节点的父子关系和下级派发权限，确保嵌套派发不会脱离原批次契约。
- 第 4 项在真正发起并发调用前提供共享资源和写入重叠结论；资源冲突可能把一个原本可并行的批次拆成多个波次。
- 第 5 项保存批次、波次、节点派发尝试和已绑定 Agent 身份，使 compact/resume 后可以只继续未完成节点。
- 第 6 项按批次或依赖集合等待，不把一次 mailbox 事件误当成整批完成。
- 第 7 项消费逐节点派发结果，允许只恢复失败或身份未确认的节点，并根据组策略决定是否停止剩余未启动节点。
- 第 8 项消费每个节点的 individual `TaskResult`，区分“部分已完成”和“整批完成”，不从派发成功推断业务结果。
- SG-F07 只诊断批次容量不足、部分派发失败、重复尝试和未映射身份等事实，不替批次选择重试或取消策略。

#### 跨功能排除

- SG-F05 的 `StateStore` 并发测试继续证明存储层原子性；批量容量和派发波次不应归并进该单任务存储功能。
- SG-F06 的 `failed`、`platform_error` 和 `interrupted` 等 individual 结果/生命周期语义不能直接当作批次状态；组级状态由第 5、7、8 项共同定义。
- SG-F04 只消费未来批量协议在发布缓存中的版本兼容结论，不管理运行时槽位或批次事务。

### 3. 改进建议

建议把“批量派发”定义为协调计划的一次显式运行操作，而不是连续若干次没有共同身份的 `spawn_agent` 调用。可以采用 `coordination_id` 加 `wave_id`/`dispatch_attempt_id` 的短期派发信封，最终名称留待统一方案确定。

#### 用户展示与实际调用分层

- 主对话保留一张简洁批量表格，说明批次目标、节点、当前波次、并行/串行理由和需要用户决策的事项。
- 每个实际 Agent 调用仍发送独立且完整的 dispatch prompt，包含自己的目标、范围、禁止事项、完成条件、上下文策略、治理等级和终态回传要求。
- 表格不作为 Hook 的唯一输入；Hook 不读取主线程 transcript，也不从表格文本猜测批次成员。

#### 建议的机械字段与校验

- 机械字段候选：`coordination_id`、`wave_id`、节点 `task_ref` 列表、每个节点的 dispatch attempt、计划顺序、当前批次策略和有界容量提示。
- AI 字段候选：本批次为什么并行、为什么分波、依赖已满足的业务理由、槽位不足时的父任务处理建议。
- 脚本应校验节点属于已验证计划、依赖已经就绪、同一节点没有活动中的重复 attempt、批次顺序稳定、节点和文本数量有上限。
- 脚本不应宣称已经预留平台槽位；`max_parallel` 即使存在，也只能是父 Agent 的上限提示或波次计划值，实际可用容量由原生平台调用结果确认。

#### 容量不足与部分失败

- 不把批量派发做成全有或全无事务；一个节点成功后，其他节点失败或尚未启动时，必须保留已成功节点和其 Agent 身份。
- 槽位不足时由父 Agent 根据计划继续下一波，不由插件后台排队；缺少结构化平台错误时，只能记录有界的 `dispatch_failed`/容量疑似事实，不能解析错误文本臆测根因。
- 重试只针对失败、未绑定或明确允许重建的节点，并使用新的 attempt 身份引用原节点；不得整批重派已成功或仍在运行的节点。
- 如果一个节点失败会使依赖节点失去前置条件，后续节点应保持未就绪并进入组级待处理状态，而不是自动当作成功或直接创建替代 Agent。

#### 平台并发边界

- 不在 Schema、Skill 或运行时代码中硬编码当前会话看到的槽位数字；容量是平台事实或父 Agent 观察到的运行条件。
- 仓库可以验证波次计算、上限和不重复派发逻辑，但不能仅凭 fixture 证明 Codex 平台真实槽位、排队顺序或跨 provider 行为。
- 真实验收至少要覆盖：槽位充足、槽位不足、一个 spawn 失败、响应缺少身份、网络断流后继续等待以及只恢复失败节点。

### 4. 可以顺手直接实施的内容

本项没有适合现在孤立修改的运行时代码、Schema、Skill 或测试。

现在直接修改 `SKILL.md` 增加批次字段或并发上限，会先于协调计划、状态模型和原生平台证据形成不可执行承诺；直接修改 `StateStore` 则会与 SG-F05 的版本、裁剪、SessionEnd 和身份绑定方案同时耦合。

现有逐次派发失败后保留其他任务记录的行为可以作为未来实现的低层基础，但它不是完整批量语义，不应现在改写成批量成功或部分成功状态。

本轮可直接完成的仍是盘点文档记录；不重命名 `tests/test_concurrency.py`，不新增临时批次 fixture，也不实际调用或模拟真实 Agent 槽位。

### 5. 必须留待最终统一方案的内容

- 批次信封的最终字段、Schema、`wave_id`/attempt 身份和与 `CoordinationPlan` 的引用关系。
- `max_parallel`、波次大小和平台即时容量之间的关系；是否允许用户指定上限，以及超过上限时由谁决定继续。
- 部分 spawn 失败、响应缺少 Agent 身份、PostToolUse 缺失、网络断流和平台拒绝的统一阶段枚举及证据字段。
- 批次是否允许动态追加节点、取消未启动节点、重新规划依赖或只恢复失败节点。
- 批量等待选择“任意一个、全部、依赖集合”与批次波次之间的关系。
- 批次状态与 individual `pending`、`dispatched`、`running`、`failed`、`platform_error`、`interrupted` 的映射，尤其是当前未实际写入的 `dispatched` 和 `unmapped running`。
- 真实 Codex/provider 对并发槽位、部分派发回调、响应字段、重复调用和跨 compact/resume 的保证；仓库 fixture 不能替代这些证据。

### 6. 不再作为目标的内容

- 不把用户可见批量表格当作可执行的批次状态或平台排队协议。
- 不把固定槽位数量写死为插件或项目的永久保证。
- 不把一次批量调用设计成失败即回滚全部成功 Agent 的原子事务。
- 不因一个 Agent 的平台错误、网络断流或槽位不足而自动重派整批已成功任务。
- 不在插件内创建后台队列、轮询器或替代原生 `spawn_agent` 的调度层。

### 7. 测试与证据

- 现有 `tests/test_concurrency.py` 仅覆盖 32 个并发 spawn 对同一 session 状态文件的写入不丢失；它没有批次身份、槽位、波次、部分失败或重试测试。
- `tests/test_governance.py` 已覆盖单次 spawn 的 `tool_use_id` 绑定、事件 ID 漂移、同名歧义不猜测、成功但无 Agent 身份和派发失败，但这些都是 individual task 证据。
- 当前没有批次生成、依赖就绪、波次排序、容量上限、部分成功保留、失败节点定向重试或禁止重复派发的 fixture。
- 单元测试只能证明 Hook 对模拟响应的处理，不能证明真实平台的并发槽位、排队、网络恢复或父任务继续等待。

### 8. 本项结论

- “批量派发与并发容量”必须保留，但应定位为第 1 项计划的运行执行层，不是单独的调度平台。
- 当前批量能力只有用户说明和逐次 spawn 的低层行为；没有正式批次身份、波次、容量、部分失败或幂等协议。
- 后续实现应保留每个已成功 Agent，按节点独立记录失败和身份未确认，使用父 Agent 显式控制波次与继续等待，不因单点失败重派整批。
- 当前不修改运行时代码、Schema、Skill 或测试，只把批量信封、容量边界和部分失败规则记录为最终统一方案输入。

## 五、第 3 项：父子层级与治理规则传播

### 1. 当前情况

当前 individual `TaskContract` 只有 `child_agents=allow|deny`，它表达“当前 Agent 是否被允许继续派发下级 Agent”的一个布尔边界，但不能表达父任务身份、允许的层级、可转交范围、模型和强度上限、上下文限制、终态回传链或下级任务与协调计划的关系。

现有行为如下：

- Skill 要求 standard 任务说明是否允许下级子 Agent，显式 strict 使用 `【下级子 Agent】<禁止 | 允许及边界>`，但没有定义“边界”必须包含哪些稳定字段。
- `auto` 在明文中看到 `【下级子 Agent】允许` 时选择 strict，并保存 `mode_reason=auto:child-agents`；这只是治理强度升级，不会创建父子任务关系。
- `_task_contract()` 只把以“允许”开头的自然语言压缩为 `allow`，其他内容统一变成 `deny`；“允许及边界”中的业务限制不会进入结构化状态。
- `TaskContract`、Schema 和 `StateStore` 都没有 `parent_task_id`、`parent_agent_id`、`root_coordination_id`、`depth`、`lineage` 或 delegation policy。
- 当前治理信封会告诉每个 Agent 保留任务 ID、实际执行并报告终态，但不会告诉运行时该结果应沿哪条父子链回传，也不会记录父 Agent 是否仍在等待其下级任务。
- 当前工作规范已经要求：当允许下级 Agent 时，必须把 20 分钟等待、目标范围巡检、同 Agent 有限恢复和终态通知规则明文写入派发 prompt，隔离上下文或独立新会话尤其不能依赖隐式父线程历史。仓库 Skill 包含通用等待规则，但没有把这一整套规则明确绑定到“允许下级 Agent”的 prompt 生成要求，运行时也不机械验证传播结果。
- 原生 `spawn_agent` 在子 Agent 内再次调用时仍可能触发同一 Hook，但当前 Hook 只能看到新的单任务派发参数，无法从现有字段确认它来自哪个受治理父任务或是否超出父任务授权。
- 当前唯一直接相关测试只证明 `child_agents=allow` 会让 `auto` 选择 strict；没有真实 nested spawn、父子映射、孙级 Agent、最大层级、授权收窄或逐级终态通知测试。

因此，现状的 `child_agents` 是单任务风险和提示字段，不是父子治理协议。strict 只能提高契约和证据要求，不能被描述成已经解决下级 Agent 的身份、权限、等待或闭环问题。

### 2. 与前后文的交接

#### 上游交接

- SG-F01 继续拥有 individual `TaskContract` 的目标、范围、禁止事项、完成条件、治理等级、模型和上下文策略；本项只定义这些授权如何传给下级任务并保持父子引用。
- 第 1 项提供 `coordination_id`、任务节点和静态任务图；嵌套派发应把新节点关联到已有计划或明确创建子协调计划，不能仅凭 canonical path 推断父子关系。
- 第 2 项提供实际派发波次和 attempt；本项决定哪些节点或 Agent 有权继续派发，以及下级派发是否占用原协调计划的容量预算。
- 父 Agent 或 AI 负责说明为什么需要下级 Agent、允许转交什么业务和完成条件；脚本只校验父子引用、枚举、上限和授权不扩张。

#### 下游交接

- 第 4 项消费父子授权中的可写范围和共享资源边界，判断下级任务是否与父任务或兄弟任务发生重叠；本项不机械推断文件冲突。
- 第 5 项保存父任务、子任务、Agent 和 session 之间的稳定映射，使 compact/resume 后能够恢复整条 lineage。
- 第 6 项按父子关系确定谁等待谁、哪个 mailbox 事件唤醒哪个父任务，以及孙级任务尚未结束时父任务是否可以关闭。
- 第 7 项决定父任务或子任务中断、平台错误和恢复动作是否向下传播；本项只提供传播路径和授权策略，不执行中断或恢复。
- 第 8 项按父子层级汇聚 individual `TaskResult`，子 Agent 的结果先交给直接父 Agent，再由父 Agent完成自己的结果和向上回传；本项不生成聚合结果。
- SG-F07 消费 lineage、授权来源、传播状态和断链事实进行诊断，不替父 Agent决定是否允许再次派发。

#### 跨功能排除

- SG-F03 继续拥有对一个明确既有 Agent 的通信结构；父子关系只帮助选择目标和回传路径，不创建批量广播或第二套父子消息系统。
- SG-F05 继续拥有 individual wait、平台对账、同 Agent 恢复和 Session 生命周期；本项只要求这些规则在允许下级 Agent 时被显式传递，并记录谁承担等待责任。
- SG-F06 继续拥有 individual 终态格式、结果验收和父任务动作；本项不要求每个孙级结果直接越级发送给根 Agent。
- SG-F04 只负责未来父子协议随版本发布和跨缓存兼容，不决定层级或授权策略。

### 3. 改进建议

建议把 `child_agents` 从单一布尔值升级为“是否允许”加稳定 delegation policy，并把父子机械引用放入协调计划或独立的 delegation envelope；不要把全部层级字段继续堆进自然语言 `【下级子 Agent】`。

#### AI 提供的业务内容

- 为什么允许当前 Agent 继续派发，以及下级 Agent 可以解决哪些子问题。
- 可转交的业务范围、明确禁止范围、完成条件和证据要求。
- 哪些背景必须传给下级 Agent，哪些父线程历史不应继续继承。
- 下级结果应怎样帮助当前父任务继续，而不是让孙级 Agent直接替根任务作最终业务结论。

#### 脚本生成或机械维护的字段

- `parent_task_id`、`root_coordination_id`、当前 `task_id`、可选 `parent_agent_ref` 和稳定 lineage。
- `depth`、`max_depth`、可选 `max_children` 及节点/attempt 引用。
- `child_agents` 的合法枚举，以及 delegation policy 的协议版本、生成时间和完整性字段。
- 模型、推理强度、上下文和治理等级的允许范围或上限；最终字段名称与约束方式留待统一方案决定。
- 直接父任务的终态回传目标，以及等待、巡检和有限恢复责任的机械引用。

#### 授权传播规则

- 父任务为 `deny` 时，下级任务不得重新开放子 Agent；父任务为 `allow` 时，下级任务只能在父任务授权范围内继续收窄，不能扩大业务范围、写入权限、最大层级或模型/强度预算。
- 每次下级派发仍应形成完整 individual contract；不能只发送 `parent_task_id` 或引用父任务后要求下级 Agent自行查找隐式历史。
- 隔离上下文、有限继承或独立新会话时，派发 prompt 必须明文包含终态通知、20 分钟等待、目标巡检、同 Agent 有限恢复和异常终态处理责任；不能只引用“遵循父任务规则”。
- 子任务完成、阻塞或需要决策时，主要回传给直接父 Agent；父 Agent吸收结果后再形成自己的终态或组级汇聚，避免孙级结果绕过中间任务责任。
- 只有平台提供稳定父任务身份或 prepared delegation 引用时，Hook 才能机械建立 lineage；正文不透明时不得通过目标文本、任务名或相邻调用猜测父子关系。

#### 最低机械校验

- 父任务引用存在且属于允许继续派发的活跃治理任务。
- 新任务深度不超过父任务上限，授权范围和策略没有比父任务更宽。
- 父子引用无自引用、循环 lineage 或悬空父节点。
- 每个下级派发具有独立任务 ID、完成条件和终态回传目标。
- 只检查引用、枚举、上限和结构完整性，不判断业务拆分是否合理或下级 Agent能力是否足够。

### 4. 可以顺手直接实施的内容

有两项边界明确的规则澄清可以在后续获得相应文件修改授权后局部实施，但本盘点任务不直接修改 Skill、参考文档或测试：

1. 在 Skill 的 `【下级子 Agent】<允许及边界>` 后明确列出必须说明的最低边界，并要求隔离上下文时把等待、目标巡检、同 Agent 有限恢复和终态通知规则明文写入下级 dispatch prompt。
2. 在治理等级参考和一致性测试中明确：允许下级 Agent 会提高治理强度，但 strict 只代表证据和契约强度，不等于已经建立父子身份、授权传播或终态汇聚。

这些调整只澄清已经确认的工作规范，不应提前发明 `parent_task_id`、最大层级或跨 session 存储结构。

当前不适合直接修改 `_task_contract()` 或 Schema：如果只把更多自然语言压进 individual contract，却没有协调计划、父子引用和状态迁移，仍然无法建立可恢复的 lineage。

### 5. 必须留待最终统一方案的内容

- delegation policy 的最终 Schema、字段归属，以及它与 `TaskContract`、`CoordinationPlan` 和 prepared contract 的引用关系。
- `parent_task_id`、`parent_agent_ref`、`root_coordination_id`、`depth`、`max_depth`、`max_children` 的必填条件和顶层任务表达方式。
- 父任务、子任务和孙任务位于相同或不同 session 时的稳定索引、存储位置、版本和 compact/resume 恢复方式。
- 下级任务的模型、推理强度、上下文继承、治理等级和并发容量如何继承、收窄或显式覆盖。
- 父任务权限与下级任务工作范围发生重叠、扩大或无法机械比较时，是拒绝、告警还是请求用户决策。
- 父任务停止、中断或进入 `needs_decision` 时的向下传播，以及子任务仍运行或迟到返回时的组级处理；具体执行归第 7 项。
- 孙级结果、阻塞和决策请求如何沿 lineage 向上汇聚，同时保留 intermediate parent 的责任和结果引用。
- 原生 Codex 是否为 nested spawn 提供稳定父 Agent、父 task path、session 和跨层级可见性字段；没有真实平台证据前不能把 fixture 当作保证。

### 6. 不再作为目标的内容

- 不继续把 `child_agents=allow|deny` 描述成完整父子治理协议。
- 不把 auto 提升 strict 描述成已经完成父子映射、授权传播或结果汇聚。
- 不允许下级 Agent只引用父任务或依赖隐式完整历史来获得目标和边界。
- 不让下级任务扩大父任务授权、写入范围、层级、并发或模型预算。
- 不要求孙级 Agent绕过直接父 Agent，向根 Agent重复发送同一终态结果。
- 不根据 `task_name`、canonical path 末段、目标文本或调用先后猜测父子关系。

### 7. 测试与证据

- `test_auto_promotes_to_strict_when_child_agents_are_allowed` 只验证 `auto` 选择 strict、保存 `child_agents=allow` 和 `mode_reason=auto:child-agents`。
- strict 字段测试只验证 `【下级子 Agent】` 标签是否存在，不验证允许范围、等待规则传播、最大层级或父子引用。
- 当前没有 nested `spawn_agent`、父子/孙级映射、跨 session lineage、授权收窄、最大层级、子任务终态回传链或父任务关闭条件测试。
- `SubagentStart`、Agent 映射和 canonical path 测试只证明单 Agent 身份绑定，不能证明平台会提供父 Agent 身份或 nested task path 语义。
- 未来应增加 delegation policy 生成与 Schema、父子引用完整性、授权单调收窄、层级上限、隔离上下文规则传播、孙级终态逐级回传和跨 compact/resume 恢复测试；真实 nested Agent 行为仍需单独平台验收。

### 8. 本项结论

- “父子层级与治理规则传播”必须保留，是现有 `child_agents` 字段需要重点改造的正式归属。
- 当前 `allow|deny` 和 auto strict 只能表达风险信号，不能证明下级 Agent受到父任务契约约束或形成可恢复 lineage。
- 目标方案应让授权逐级收窄、规则显式传递、结果逐级回传，并用稳定机械引用连接父、子、孙任务。
- 本轮只更新 SG-F08 盘点文档；局部 Skill/参考规则澄清和完整结构化实现均留待相应授权及最终统一方案。

## 六、第 4 项：共享资源与写入冲突协调

### 1. 当前情况

当前 `TaskContract` 只有自然语言 `scope` 和 `forbidden`，没有结构化的读取范围、写入范围或资源所有权。`strict` 会用于并发写入风险任务，但只提高契约和证据要求，并不能阻止两个 Agent 同时修改同一文件。

多个 Agent 可以共享同一工作区，但 Hook 不观察每一次文件读写，也不能证明 Agent 实际遵守了自然语言范围。`StateStore` 的文件锁只保护治理状态 JSON，不保护项目源码、Git index、生成文件或包管理器状态。SG-F04 的发布锁、重装锁和原子写入是具体发布事务保护，不能直接充当通用 Agent 资源锁。

当前并发测试只证明治理状态写入不丢记录，没有文件重叠、工作树冲突、Git 冲突或结果覆盖测试。因此，现状不能证明“多个 Agent 同时写入同一工作区是安全的”，也不能把 strict 描述成已经获得文件互斥权。

### 2. 与前后文的交接

#### 上游交接

- 第 1 项的协调计划为每个任务节点提供资源声明位置。
- 第 2 项根据资源冲突把任务分成不同派发波次。
- 第 3 项限制下级 Agent 不得扩大父任务允许的写入范围。
- SG-F01 继续拥有单任务业务范围；本项把其中可机械识别的资源边界独立结构化。
- AI 负责判断任务实际需要哪些资源、是否允许共享以及为什么可以并行；脚本只校验声明结构和可机械识别的重叠。

#### 下游交接

- SG-F05 提供资源声明的持久化底座，但不负责保护业务文件。
- 第 5 项需要保存哪些资源当前由哪些任务占用。
- 第 7 项处理 Agent 异常退出后资源声明如何释放或转为待对账。
- SG-F07 诊断资源冲突、声明缺失和迟到释放，但不决定业务上是否可以并行。
- SG-F04 的发布路径、Marketplace、缓存和全局入口属于具有特殊风险的逻辑资源，应继续由发布功能定义具体操作门禁。

#### 跨功能排除

- 不把 `StateStore` 的 session 锁描述成源码或工作区锁。
- 不把 SG-F04 的发布事务锁扩展成全局 Agent 资源锁。
- 不把资源声明当作沙箱、权限系统或操作系统级强制互斥。
- 不重复 SG-F01 的业务范围判断，也不让本项决定任务结果是否正确。

### 3. 改进建议

建议为协调计划中的每个节点增加结构化 `ResourceClaim` 或等价声明，至少表达：

- 资源类型：文件、目录、Git 工作树、Git index、生成目录、运行缓存或其他逻辑资源。
- 访问方式：`read`、`write` 或 `exclusive`。
- 明确路径或稳定逻辑名称。
- 所属任务节点和协调组。
- 冲突处理建议：并行、串行或请求决策。

职责划分：

- AI 负责判断任务实际需要哪些资源、是否允许共享以及为什么可以并行。
- 脚本负责路径规范化、引用存在性、访问枚举和确定性的范围重叠检查。
- 脚本不根据目标文本或关键词猜测真实资源，也不判断两个业务修改是否“应该能够自动合并”。

建议的默认冲突规则：

- `read` 与 `read` 可以并行。
- 重叠范围的 `write` 与 `write` 默认不得并行，应拆成不同波次。
- `read` 与 `write` 重叠时默认串行；只有明确使用稳定快照或其他安全边界时才能并行。
- Git index、提交、分支切换、依赖安装和共享生成目录应视为工作区级独占资源。
- 用户已有未提交修改不是可被 Agent 覆盖的资源，应作为必须保留的外部状态。

这些声明首先是协调和诊断依据，不应宣称为操作系统级权限或强制文件锁。资源重叠检测应在派发波次决定前完成，实际文件写入仍由原生 Agent 和工作区规则负责。

### 4. 可以顺手直接实施的内容

有两项低耦合规则澄清可以在确认后单独实施，但本盘点任务不直接修改 Skill、参考文档或测试：

1. 在 Skill 和治理等级说明中明确：提升到 strict 不会自动解决写入冲突，父 Agent 仍须拆分写入范围或改为串行。
2. 增加规则一致性测试，防止以后把 strict 错误描述成已经取得文件所有权或互斥锁。

现在不适合直接给 `TaskContract`、Schema 或 `StateStore` 增加资源字段，因为资源形状、路径规则、状态生命周期和冲突策略尚未统一。

### 5. 必须留待最终统一方案的内容

- `ResourceClaim` 的正式 Schema、协议版本和存储位置。
- 文件、目录和逻辑资源的统一表示方式。
- 相对路径、工作区根、大小写、符号链接和目录包含关系的规范化规则。
- 写入重叠时选择拒绝、改为串行、警告或请求用户决策的统一策略。
- 是否需要资源所有权、租约或仅保存提示性声明。
- Agent 结束、异常、恢复、中断和迟到事件发生时的资源释放规则。
- 跨 session、父子 Agent 和 compact/resume 后的资源占用恢复。
- Git index、分支、依赖安装、测试生成物和用户已有修改等工作区级资源模型。
- 多 Agent 真实并发写入、读写竞争、Agent 异常退出和迟到写入测试。

### 6. 不再作为目标的内容

- 不把 strict 治理等级当作文件锁、租约或权限边界。
- 不让 Hook 通过自然语言关键词自动判断真实写入范围或业务合并安全性。
- 不因声明了资源范围就宣称插件能够阻止 Agent 越界写文件。
- 不把 SG-F05 的状态锁、SG-F04 的发布锁或普通原子写入描述成跨 Agent 通用协调机制。
- 不在插件内创建新的文件操作代理、工作区守护进程或第二套调度平台。

### 7. 测试与证据

- `tests/test_concurrency.py` 只覆盖 32 个并发 spawn 对同一 session 状态文件的写入不丢失，不覆盖业务文件或资源范围冲突。
- `tests/test_governance.py` 的 strict/auto 测试只证明并发写入属于严格治理信号，不证明共享资源已经互斥。
- SG-F04 的发布和重装锁测试只证明具体发布事务的并发保护，不是多 Agent 资源协调证据。
- 当前没有 `ResourceClaim` Schema、路径规范化、目录包含关系、读写矩阵、重叠拒绝、波次拆分、锁释放或异常遗留测试。
- 未来应增加纯机械资源声明和重叠判定测试，再增加受控多进程文件写入、异常退出、迟到释放、用户 dirty worktree 和真实平台并发验收；fixture 不能单独证明 Agent 遵守声明。

### 8. 本项结论

- “共享资源与写入冲突协调”必须保留，是 SG-F08 将并发派发从“状态不丢记录”提升到“工作区边界可诊断”的核心功能。
- 当前没有结构化资源声明，也没有阻止或检测业务文件写冲突的机制；strict 只能提高治理强度，不能代替资源互斥。
- 目标方案应由 AI 声明资源和并行理由，由脚本检查路径、访问模式和范围重叠，再由父 Agent 选择并行、串行或请求决策。
- 本轮只记录 SG-F08 盘点结论，不修改运行时代码、Schema、Skill、测试或其他功能文档。

## 七、第 5 项：协调组状态与会话恢复

### 1. 当前情况

`StateStore` 当前按 `session_id` 保存扁平的 `tasks`、`agents` 和 `health`，没有协调组记录。SessionStart 可以恢复最近 12 小时内的单任务状态，包括运行中、待恢复、`platform_error` 和 `needs_decision`；恢复摘要最多展开 8 个任务，并受 1800 字符限制。

当前恢复能力只能逐条展示 individual task，无法恢复批次、依赖、父子关系、资源占用或组级进度。SessionEnd 会保留仍在运行、待恢复或需要决策的单任务，全部解决后才删除 session 状态，但如果同一协调组的父任务、子任务或孙任务分布在不同 session，当前没有稳定索引把它们重新组合起来。

当前状态锁只能保证单个 session JSON 的更新安全，无法让多个 session 的组级更新形成原子事务。状态损坏时会隔离文件并建立空的 degraded 状态；对单任务工具可以降级放行，但协调组身份丢失后若直接继续派发，可能重复创建已经存在的 Agent。

因此，当前已经具备较完整的单任务会话恢复底座，但不具备协调组恢复能力。

### 2. 与前后文的交接

#### 上游交接

- 第 1 项提供静态 `CoordinationPlan` 和计划引用。
- 第 2 项提供批次、波次和逐节点派发 attempt。
- 第 3 项提供父子 lineage。
- 第 4 项提供资源声明及占用关系。
- SG-F05 继续拥有状态文件安全、锁、版本、裁剪、SessionStart 和 SessionEnd 的底层实现。
- 本项只拥有协调组记录、节点引用、组级恢复摘要和关闭条件，不重新实现 StateStore。

#### 下游交接

- 第 6 项根据组级快照决定继续等待哪些 Agent。
- 第 7 项向组状态写入部分失败、恢复和待决策事实。
- 第 8 项写入 individual result 引用和最终聚合结果引用。
- SG-F07 读取组快照进行诊断，不修改或恢复组状态。
- SG-F04 消费组状态版本的 N/N-1 兼容要求。

#### 跨功能排除

- 不重新定义 SG-F05 的文件安全、锁、损坏隔离、状态版本和单任务状态转换。
- 不把完整任务契约、完整结果或全部诊断内容复制进协调组记录。
- 不让 SessionStart 自行调用等待、恢复、派发或中断工具。
- 不因建立组级索引而引入数据库、后台服务或第二套编排平台。

### 3. 改进建议

建议在单任务状态之上增加独立的协调组运行记录，而不是把全部组级字段复制到每个任务中。

候选结构至少包括：

- `coordination_id`、协议版本和静态计划引用或哈希。
- 根任务、根 session 和可选父协调组引用。
- 节点 `task_ref` 到 individual `task_id`、Agent 身份和 attempt 的映射。
- 每个节点的依赖、资源声明及结果引用。
- 最近事件、更新时间、待处理节点和 action-required 引用。
- 组级 revision、关闭状态和必要 tombstone。

职责上应保持：

- individual task 状态仍是单任务生命周期的权威来源。
- 协调组记录保存关系、索引和组级摘要，不复制完整任务正文或结果内容。
- 组级状态应从节点状态、依赖和待处理动作计算，不能再用一个平面 `status` 混合执行、结果和用户动作。

SessionStart 建议按协调组恢复：

- 优先展示协调组 ID、整体目标摘要、已完成/运行中/失败/待决策节点数量。
- 展示当前必须处理的节点及下一步，而不是把所有节点逐条塞入上下文。
- 明确提醒不得重复派发已经存在的 Agent。
- 完整计划和结果通过稳定引用按需读取，不进入普通恢复摘要。

SessionEnd 建议：

- 只在协调组真正关闭，或仍需保留的组记录已经转移到稳定索引后，才允许删除相关 session 状态。
- 对跨 session 组不能因为某一个 session 结束就删除整个协调关系。
- 保存关闭版本或 tombstone，防止晚到事件重建已关闭任务。

跨 session 组无法依赖多文件原子事务时，应记录版本、事件身份和可重放的引用，通过对账恢复一致性，不应宣称多个状态文件已经原子提交。

### 4. 可以顺手直接实施的内容

目前没有适合直接修改的运行时代码。

当前 SessionStart/SessionEnd 已经完成的单任务修补应保留：

- 恢复 `platform_error` 和 `needs_decision`。
- 按 action-required 优先级展示。
- SessionEnd 保留未解决任务。
- 使用锁内条件删除。

可以低耦合补充的只有说明和测试命名：

- 明确现有 SessionStart 是“单任务恢复摘要”，不是协调组恢复。
- 明确 SessionEnd 的保留行为只针对当前 session 内可见任务。

在没有正式组结构前，不应直接增加 `groups` 字段或修改 SessionStart 输出。

### 5. 必须留待最终统一方案的内容

- 协调组状态的正式 Schema、版本、存储位置和容量限制。
- 同 session 与跨 session 协调组是否采用同一种索引结构。
- 静态计划、运行组状态和 individual task 状态之间的权威关系。
- 跨多个状态文件更新时的一致性、重放和对账协议。
- 组级执行状态、业务结果和 action-required 的分层模型。
- SessionStart 的组级排序、摘要长度、按需展开和去重规则。
- SessionEnd、状态裁剪、归档、关闭和 tombstone 生命周期。
- 状态损坏或组索引缺失时如何避免重复派发。
- N/N-1 运行缓存读取组状态的兼容和迁移门禁。
- compact/resume、跨 session、晚到事件和真实网络断流恢复测试。

### 6. 不再作为目标的内容

- 不把当前逐条 individual task 恢复摘要描述成协调组恢复。
- 不通过扫描 `task_name`、canonical path 或目标文本事后重建组关系。
- 不在组记录中复制全部任务 prompt、完整结果或长错误文本。
- 不把跨多个 session 文件的顺序写入描述成原子事务。
- 不因状态降级或组索引缺失而自动整批重新派发。
- 不让 SessionStart 或 SessionEnd 变成后台调度器。

### 7. 测试与证据

- 当前 SessionStart 测试覆盖单任务目标、完成条件、Agent 身份、action-required 优先级、遗漏计数、坏记录跳过和 1800 字符边界。
- 当前 SessionEnd 测试覆盖未解决单任务保留、全部任务解决后删除、stale/action-required 记录保留和清理失败降级。
- `tests/test_concurrency.py` 只证明单个 session 中的并发任务记录不丢失，不覆盖协调组或跨 session 一致性。
- 当前没有组状态 Schema、计划引用、节点映射、跨 session 索引、组级恢复摘要、组关闭、tombstone 或组状态损坏测试。
- 未来应覆盖同 session 与跨 session 组、compact/resume、不重复派发、部分节点状态恢复、SessionEnd 条件保留、多文件更新中断和晚到事件；真实 Codex 会话恢复行为仍需单独平台验收。

### 8. 本项结论

- “协调组状态与会话恢复”必须保留，但应建立在 SG-F05 的单任务状态安全和 Session 生命周期底座之上。
- 当前 SessionStart/SessionEnd 已能保护单任务待办，不能恢复任务图、批次、父子、资源或组级结果。
- 目标方案应保存有界的关系和引用，按组恢复关键待办，并在跨 session 场景使用可对账协议而不是虚构原子事务。
- 本轮只更新 SG-F08 盘点文档，不修改运行时代码、Schema、Skill、测试或其他功能文档。

## 八、第 6 项：多目标等待与事件路由

### 1. 当前情况

当前 Skill 只规定父 Agent 保存单个 Agent ID/canonical path 后调用一次 `wait_agent`，超时后再对该目标调用 `list_agents`。`wait_agent` 没有 Hook matcher，插件不观察等待开始、等待结束或 mailbox 唤醒，也没有后台定时器。

mailbox 消息、完成通知、用户输入和平台错误由 Codex 原生等待工具提前返回；这些事件不是插件自己生成的状态事件。`list_agents` 的 PostToolUse 可以逐个对账返回中的多个 Agent，但只更新 individual task 的 `platform_status` 或 `platform_error`，不会形成批量等待结果。

父 Agent 当前需要自己维护多个 Agent 的等待顺序；没有“等待任意一个”“等待全部”“等待某个依赖集合”或“某个 Agent 先返回后继续等待其余 Agent”的结构化策略。超时本身不被视为失败，只有明确平台错误才进入恢复流程，但这个单目标规则目前没有扩展到任务组。

现有测试覆盖单目标等待规则和单 Agent `list_agents` 对账，没有多目标等待、首事件唤醒、继续等待其余任务或批量超时测试。因此，当前只能证明父 Agent 可以按规则等待一个 Agent 并按需巡检，不能证明多 Agent 等待已经形成协调能力。

### 2. 与前后文的交接

#### 上游交接

- 第 1 项提供依赖图和就绪集合，决定哪些节点应该一起等待。
- 第 2 项提供批次和波次，决定当前等待的是哪个派发阶段。
- 第 3 项提供父子关系，决定谁等待谁、哪个事件应回传给哪个父任务。
- 第 5 项保存等待 checkpoint、节点映射和会话恢复摘要。
- SG-F05 继续拥有单 Agent 等待规则、平台对账、状态转换和恢复次数；本项只负责多目标组合策略。

#### 下游交接

- 第 7 项消费单个目标的异常或平台错误，决定只恢复该 Agent 还是影响其他节点。
- 第 8 项消费等待集合中的 individual results，判断组级结果是否可以汇聚。
- SG-F03 继续负责面向明确目标 Agent 的通信和 follow-up，不创建批量等待消息系统。
- SG-F07 只诊断等待集合缺失、唤醒原因、目标断链和部分事件，不主动调用等待或恢复工具。

#### 跨功能排除

- 不重新实现 SG-F05 的 20 分钟单目标等待、目标巡检和平台对账状态转换。
- 不为 `wait_agent` 新增 Hook matcher或后台定时器。
- 不把 mailbox、用户输入或平台唤醒描述成插件自己生成的事件。
- 不创建新的终态消息通道或批量通信协议。

### 3. 改进建议

建议为协调组增加显式 `WaitPolicy`，至少区分：

- 等待任意一个节点。
- 等待全部节点。
- 等待某个依赖集合。
- 等待指定节点或当前波次。

机械字段可以包括：

- `wait_id`。
- `coordination_id`。
- 目标节点或依赖集合引用。
- 等待策略枚举。
- 期望唤醒事件枚举。
- 超时策略。
- 每个目标当前是否仍在等待。
- 最近一次巡检结果和唤醒原因。

AI 负责说明为什么选择某种等待方式，以及某个节点先返回后父任务应做什么；脚本只负责校验目标引用、策略枚举、集合完整性和状态一致性。

行为上应明确：

- 一个 Agent 先返回时，只更新该节点，不自动取消其他节点的等待。
- 一个 Agent 出现 `platform_error` 时，默认只对账和恢复该 Agent，其他任务继续等待；是否取消剩余任务由组策略决定。
- 超时不等于失败，必须记录为等待超时或待巡检事实。
- 用户输入、mailbox 首事件、正常完成和平台错误要保留不同唤醒原因。
- 迟到、重复和乱序事件不能仅按到达顺序覆盖等待状态。
- 插件仍不提供等待器；父 Agent 继续显式调用原生 `wait_agent`、`list_agents` 和 `followup_task`。

### 4. 可以顺手直接实施的内容

有一项低耦合规则澄清可以在确认后单独实施，但本盘点任务不直接修改 Skill 或测试：

- 在 Skill 中明确“多目标等待由父 Agent 按目标集合自行组合，Hook 不提供批量等待、定时轮询或首事件调度”。

也可以增加规则一致性测试，确保：

- `wait_agent` 仍不被 Hook matcher 捕获。
- `list_agents` 只作为已发生调用的状态对账入口。
- 超时不会被描述成平台错误。

现在不适合直接修改状态枚举、SessionStart 或新增等待字段，因为它们必须和协调组状态、部分失败和恢复策略一起设计。

### 5. 必须留待最终统一方案的内容

- `WaitPolicy` 的正式 Schema、字段来源和存储位置。
- “任意、全部、依赖集合、指定目标”与批次波次及依赖状态的精确关系。
- mailbox 首事件、用户输入、超时、平台错误和正常终态的统一唤醒枚举。
- 一个目标异常时是否继续等待其他目标，以及哪些组策略允许取消剩余任务。
- 等待 checkpoint 是否持久化，以及 compact/resume 后如何恢复而不重复派发。
- 多个 `wait_agent` 调用的顺序、并行方式和平台槽位影响。
- 迟到、重复、乱序事件的去重和冲突记录。
- 真实 Codex 平台对多 Agent 等待、首事件唤醒、用户输入打断和跨 session 恢复的证据。

### 6. 不再作为目标的内容

- 不把单目标 `wait_agent` 规则描述成已经支持批量等待。
- 不把一次 mailbox 更新或一个 Agent 完成描述成整个协调组已经结束。
- 不因一个目标超时或沉默而自动标记失败、恢复或取消其他目标。
- 不在 Hook 内创建后台等待器、轮询器或主动唤醒机制。
- 不通过反复读取代码、Git、日志或测试状态猜测仍在运行的 Agent 进度。

### 7. 测试与证据

- 当前规则一致性测试证明父 Agent 使用 `timeout_ms: 1200000`、超时后目标巡检、超时不等于错误、正常运行时继续等待，以及 Hook 不注册 `wait_agent`。
- `list_agents` 测试只覆盖 individual Agent 的平台错误、普通状态、错误摘要容量和生命周期更新。
- 当前没有 `WaitPolicy` Schema、任意/全部/依赖集合等待、首事件唤醒、一个完成后继续等待其余节点、批量超时或等待 checkpoint 测试。
- 单元测试和 fixture 不能证明真实 Codex mailbox、用户输入、多个原生 wait 调用或平台唤醒顺序。
- 未来应增加等待策略生成和引用校验、逐目标状态更新、唤醒原因、重复/迟到事件、compact/resume 和部分平台错误测试，并单独执行真实平台验收。

### 8. 本项结论

- “多目标等待与事件路由”必须保留，但应定位为父 Agent 组合原生等待工具的组级策略，不是 Hook 内部调度器。
- 当前只有单目标等待和 `list_agents` 对账规则，没有任意/全部/依赖集合等待、首事件路由或继续等待其余任务的结构化能力。
- 目标方案应保留逐目标状态、明确唤醒原因和等待 checkpoint，并在一个 Agent 发生事件时继续维护其他 Agent 的等待关系。
- 本轮只更新 SG-F08 盘点文档，不修改运行时代码、Schema、Skill、测试或其他功能文档。

## 九、第 7 项：部分失败、独立恢复与中断传播

### 1. 当前情况

当前 `list_agents` 会分别更新每个已映射任务；一个 Agent 被标记为 `platform_error` 时，不会自动修改其他任务状态。单任务平台错误允许对同一 Agent 自动恢复一次，恢复后再次确认错误会进入 `needs_decision`。

当前恢复没有稳定的 `recovery_attempt_id` 或原子占位，并发 follow-up 可能形成重复恢复。`interrupt_agent` 一次只处理一个明确目标；成功后只把对应任务标记为 `interrupted`，不会自动中断兄弟、子级或整个协调组。中断和恢复都没有组级影响范围或传播策略。

当前没有 `partial_failure`、失败影响节点、暂停依赖节点或继续独立分支等组级记录。部分 spawn 失败、运行期平台错误、业务阻塞和主动中断都只落到 individual task 状态，父 Agent 需要自行判断如何处理其他任务。

成功中断只证明治理状态已记账，不能证明远端模型或 provider 请求已经物理终止。现有测试只覆盖单任务恢复上限、中断和迟到事件保护，没有证明一个任务失败时其他任务保持运行，也没有传播范围测试。

因此，当前有“单任务错误不会主动批量改写其他任务”的低层隔离基础，但没有正式的部分失败和组级恢复协议。

### 2. 与前后文的交接

#### 上游交接

- 第 1 项的任务图决定失败节点会影响哪些依赖节点。
- 第 2 项提供派发和重试 attempt，部分 spawn 失败属于本项输入。
- 第 3 项提供父子 lineage，决定中断或关闭是否存在向下传播路径。
- 第 4 项决定失败、中断或未知结果后资源声明能否释放。
- 第 5 项保存部分失败、待恢复、待决策和中断结果。
- 第 6 项确保一个 Agent 失败时其他独立 Agent 可以继续等待。

#### 下游交接

- SG-F05 继续拥有 individual `platform_error`、恢复次数、`retry_required`、`needs_decision` 和 `interrupted` 状态转换。
- SG-F03 继续负责恢复消息和原生 follow-up 参数，不决定恢复影响范围。
- SG-F06 提供 individual `blocked`、`needs_decision` 和结果引用；本项不重新定义单任务业务结果。
- 第 8 项根据部分失败和 individual results 计算组级结果。
- SG-F07 诊断失败影响范围、恢复 attempt 和传播结果，不执行恢复或中断。

#### 跨功能排除

- 不重新实现 SG-F05 的单任务恢复上限、中断状态机或平台错误对账。
- 不把一个节点的 individual `failed`、`blocked` 或 `platform_error` 直接等同为整个协调组失败。
- 不让 Hook 根据错误文本自动决定取消整个任务组或切换 provider。
- 不建立原子批量中断或后台自动恢复调度器。

### 3. 改进建议

建议建立明确的组级 `FailurePolicy` 和 `InterruptPolicy`。

默认处理原则应为：

- 一个节点失败时，只改变该节点及依赖它的节点。
- 与失败节点无依赖关系的任务继续运行或等待。
- 依赖节点进入“前置条件未满足”或暂停状态，而不是被自动标记为业务失败。
- 单任务平台恢复继续复用 SG-F05 的“同 Agent、有上限”规则。
- 第二次平台错误只让该节点进入 `needs_decision`，不让整个协调组自动失败。
- 只有显式组策略才允许停止尚未启动节点或中断其他正在运行的节点。

候选策略可以包括：

- `continue_independent`：继续所有不受影响的分支。
- `pause_dependents`：暂停依赖失败节点的任务。
- `halt_unstarted`：不再启动尚未派发的节点。
- `target_only`：只中断指定任务。
- `descendants`：中断指定任务及其下级任务。
- `remaining_group`：中断组内剩余任务，必须由父 Agent 或用户明确决定。

机械记录至少需要：

- 失败或中断的节点引用。
- 失败阶段和来源。
- recovery/interrupt attempt ID。
- 受影响依赖节点集合。
- 每个目标的请求结果。
- 仍继续运行的节点集合。
- 是否需要用户决策。

批量中断不能被描述成原子操作。平台一次只处理一个目标，因此必须分别记录成功、失败和未知结果，并继续保留未成功中断任务的真实状态。

### 4. 可以顺手直接实施的内容

有两类低耦合改进可以在确认后实施，但本盘点任务不直接修改 Skill 或测试：

- 在 Skill 中明确：一个 Agent 平台错误时只恢复该 Agent，继续等待其他 Agent，不得整批重新派发。
- 增加单元测试，证明：
  - 一个 Agent 进入 `platform_error` 不改变另一个 `running` 任务。
  - 中断一个 Agent 不改变兄弟任务。
  - 对一个 Agent 的恢复不会消耗其他任务的恢复次数。

这些测试可以基于当前 individual 状态行为增加，不需要先建立完整组级 Schema。

现在不适合直接实现失败传播或批量中断，因为依赖图、组状态和传播策略尚未统一。

### 5. 必须留待最终统一方案的内容

- `FailurePolicy`、`InterruptPolicy` 和恢复策略的正式 Schema。
- 部分失败、依赖暂停、继续运行和组级待决策的状态分层。
- recovery/interrupt attempt 身份、原子占位和迟到回调处理。
- 父任务、子任务和孙任务的中断传播范围。
- 部分批量中断时逐目标成功、失败和未知结果的记录方式。
- 失败或中断后的资源释放和所有权转移。
- 第二次平台错误、用户选择切换 provider、稍后重试、重建或取消的退出路径。
- 跨 session 传播、compact/resume 和迟到结果处理。
- 真实 Codex 对并发恢复、中断返回、远端终止和部分失败的证据。

### 6. 不再作为目标的内容

- 不因一个 Agent 失败、断流或达到恢复上限而自动把整个协调组标记为失败。
- 不因单点异常而整批重新派发已经成功或仍在运行的任务。
- 不把批量中断描述成平台原子操作。
- 不把成功中断记录描述成 provider 请求已经物理终止或平台错误已经修复。
- 不让依赖节点在前置失败后自动伪装成业务失败或完成。
- 不建立无限恢复、无限追问或无明确上限的自动重试链。

### 7. 测试与证据

- 当前测试覆盖 individual 平台错误、首次恢复、再次错误进入 `needs_decision`、明确失败不计恢复次数和成功恢复后再次启动。
- 当前中断测试覆盖单个运行中或 action-required 任务进入 `interrupted`、明确失败保持原状态和迟到中断不覆盖完成任务。
- 当前没有两个或更多任务场景下的失败隔离、兄弟任务保持运行、依赖暂停、传播中断、部分批量中断或组级待决策测试。
- fixture 只能证明模拟事件按当前顺序更新 individual 状态，不能证明真实平台恢复同一 Agent、中断远端执行或按预期生成迟到事件。
- 未来应先增加单任务之间互不影响的低耦合回归测试，再增加 FailurePolicy、InterruptPolicy、依赖传播、资源释放、跨 session 和真实平台部分失败验收。

### 8. 本项结论

- “部分失败、独立恢复与中断传播”必须保留，并以单任务错误隔离、独立恢复和显式传播策略为核心。
- 当前 individual 状态更新天然不会批量回滚其他任务，但没有依赖影响、部分失败、恢复 attempt 或中断传播协议。
- 目标方案应默认继续不受影响的任务，只暂停依赖分支，并且只有显式策略或用户决策才扩大中断范围。
- 本轮只更新 SG-F08 盘点文档，不修改运行时代码、Schema、Skill、测试或其他功能文档。

## 十、第 8 项：结果汇聚与组级闭环

### 1. 当前情况

当前 `task-result-v1` 只描述 individual task result，没有协调组结果或聚合结果 Schema。运行时只在部分 `SubagentStop` 成功路径中生成简化的 `result_document`。

当前 individual result 没有稳定 `result_id`、内容哈希或独立结果引用；`evidence`、`remaining` 仍固定为空数组，正文还可能被截断。SG-F06 已规划正式 `TaskResult`、`result_reference`、幂等和冲突处理，但这些仍然只解决单任务结果。

当前父 Agent 只能从多个原生回复和任务状态中人工整理结论，没有 fan-in 记录。一个 Agent 完成不会机械触发组级汇聚，也不能证明整个协调组完成。当前没有部分成功、缺失结果、冲突结论、证据去重或组级 `needs_decision` 协议，也没有稳定规则判断父任务何时可以关闭协调组。

当前测试只覆盖 individual result 的形状和单任务迟到事件保护，不覆盖多个结果的汇聚。因此，即使 SG-F06 的目标结构化结果全部实现，SG-F08 仍需要单独的组级聚合层。

### 2. 与前后文的交接

#### 上游交接

- 第 1 项提供任务图、必需节点和汇聚关系。
- 第 2 项提供实际派发节点和未派发节点。
- 第 3 项提供父子层级，决定孙级结果先汇聚到哪个直接父任务。
- 第 5 项保存 individual result 引用和组级聚合状态。
- 第 6 项决定哪些结果尚需继续等待。
- 第 7 项提供失败、暂停、中断和待决策节点。

#### 下游交接

- SG-F06 完全拥有 individual `TaskResult` 的生成、验收、持久化、幂等和父任务交接。
- 本项只引用 SG-F06 的正式结果，不重新解析 Agent 自由文本，也不修改 individual result。
- SG-F07 诊断结果缺失、冲突、不可读和聚合不完整，但不生成业务结论。
- SG-F04 消费聚合协议的版本兼容和发布门禁。

#### 跨功能排除

- 不把 individual `TaskResult` 扩展成同时承担协调计划、批次状态和组级汇聚。
- 不让 Hook 根据自由文本自动裁决多个 Agent 的业务冲突。
- 不因单个 `SubagentStop` 放行或 individual `complete` 自动关闭协调组。
- 不创建第二套结果回传通道；仍使用原生 Agent 回复和稳定结果引用。

### 3. 改进建议

建议建立轻量、版本化的 `AggregateResult`，保存 individual result 引用和父 Agent 生成的组级结论，而不是复制所有完整结果。

机械字段可以包括：

- `aggregate_result_id`。
- `coordination_id`。
- 协调计划版本或哈希。
- 纳入汇聚的 `result_reference[]`。
- 缺失、冲突、失败、中断或未决节点引用。
- 生成时间、revision 和内容哈希。
- 上一个聚合结果引用。
- 组级完整度和 action-required 状态。

AI 或父 Agent 提供：

- 整体业务结论。
- 关键证据摘要。
- 剩余事项。
- 冲突结论及处理建议。
- 是否可以接受部分结果。
- 用户需要决定的问题。
- 父任务下一步。

建议区分两个层次：

- 机械完整度：必需结果是否齐全、引用是否有效、是否存在冲突或未解决动作。
- 业务验收结果：父 Agent 判断整体任务是否完成、部分完成、阻塞或需要决策。

组级状态可以考虑：

- `complete`：所有必需节点已有可用结果，依赖闭环，父 Agent 接受整体结果。
- `partial`：取得部分有效结果，但存在明确缺失、失败或取消，并且父 Agent 决定以部分结果结束。
- `blocked`：当前无法继续，但存在明确恢复条件。
- `needs_decision`：需要用户选择后才能确定继续、取消或接受部分结果。
- `cancelled` 或 `failed`：只有在组策略和父 Agent 明确判断后使用，不能由一个节点失败自动推导。

冲突处理应满足：

- 多个 Agent 的矛盾结论不能静默覆盖。
- 保留每个结果引用、证据来源和冲突对象。
- 相同证据可按稳定引用或内容哈希去重，不能只按自然语言相似度机械合并。
- 父 Agent 负责解释和裁决业务冲突，脚本只记录引用和完整性。

组级闭环条件建议为：

- 所有必需节点已经完成、明确失败、取消或转为待决策。
- 没有仍被误认为已经结束的运行中任务。
- 所有 action-required 均已处理，或被明确保留进聚合结果。
- 聚合结果已持久化并取得稳定引用。
- 父任务已经生成面向用户的简洁摘要。

### 4. 可以顺手直接实施的内容

有一项低耦合规则澄清可以在确认后实施，但本盘点任务不直接修改 Skill 或测试：

- 在 Skill 中明确：单个 Agent 的完成通知不等于协调组完成；父 Agent 必须核对全部必需节点、失败分支和待决策事项后才能结束。

可以增加规则一致性测试，防止以后把 `SubagentStop` 放行或某个 individual `complete` 描述成组级完成。

现在不适合新增 AggregateResult 代码或 Schema，因为它依赖 SG-F06 的正式 `TaskResult`、协调计划、组状态和部分失败模型。

### 5. 必须留待最终统一方案的内容

- `AggregateResult` 的正式 Schema、生成器、存储和引用格式。
- individual result、嵌套聚合结果和最终根聚合结果之间的引用关系。
- `complete`、`partial`、`blocked`、`needs_decision`、`cancelled` 和 `failed` 的组级计算规则。
- 哪些节点是必需、可选或允许缺失。
- 结果冲突、证据去重、缺失引用和损坏结果的处理。
- 聚合结果的幂等、revision、迟到 individual result 和重新聚合规则。
- 部分完成后迟到结果是否生成新 revision，还是仅作为补充证据。
- 父任务完整聚合上下文与用户简洁摘要的分层。
- SessionStart、SessionEnd、裁剪和归档对聚合结果的保留。
- N/N-1 版本兼容以及真实 Codex 结果回传和父任务闭环证据。

### 6. 不再作为目标的内容

- 不把 individual `complete`、Agent 停止或 `SubagentStop` 放行当作协调组完成。
- 不把多个结果全文复制进 StateStore 或普通 SessionStart 摘要。
- 不让脚本通过关键词、文本长度或自然语言相似度裁决业务冲突。
- 不因一个节点失败就自动推导整个组 `failed`。
- 不静默覆盖冲突结论、缺失结果或迟到结果。
- 不让聚合生成器替父 Agent 验收业务正确性或替用户作未授权决策。

### 7. 测试与证据

- 当前 `test_successful_result_document_matches_schema` 只证明 individual `result_document` 具有必填字段和合法状态枚举。
- SG-F06 已覆盖 individual 结果的普通终态保护、冲突写入的锁内 compare-and-set 和父任务终态回传责任文字，但正式 `TaskResult`/ResultStore 仍未实现。
- 当前没有 AggregateResult Schema、多个结果 fan-in、必需/可选节点、部分成功、冲突保留、证据去重、迟到结果 revision 或组级关闭测试。
- fixture 只能证明单任务事件和当前简化结果写入，不能证明真实父任务收到多个结果、正确汇聚或生成用户摘要。
- 未来应先实现和验证正式 individual `TaskResult`，再增加聚合生成、引用完整性、组级状态、冲突/缺失、幂等重算和嵌套结果测试，并单独完成真实平台闭环验收。

### 8. 本项结论

- “结果汇聚与组级闭环”必须保留，是 SG-F08 最终把多个 individual task 转换为父任务可交付结果的闭环层。
- 当前没有组级结果对象、部分成功协议、冲突保留或组关闭条件；SG-F06 的正式 individual `TaskResult` 是必要上游，但不能替代本项。
- 目标方案应保存稳定结果引用和机械完整度，由父 Agent 生成组级业务结论，并以 `AggregateResult` 或等价对象支持幂等、冲突和迟到结果。
- 本轮只更新 SG-F08 盘点文档，不修改运行时代码、Schema、Skill、测试或其他功能文档。

## 十一、整体收口、覆盖审查与修改方案输入

### 1. 最终名称、职责与独立大功能结论

- 最终名称：**多 Agent 协调与组级闭环**。
- 一句话职责：在不替代 Codex 原生 Agent 工具的前提下，把多个 individual task 组织成具有稳定任务图、资源边界、独立恢复和组级结果闭环的协调任务组。
- 主要入口：父 Agent 生成协调计划并按节点调用原生 `spawn_agent`；运行时当前只有 individual spawn、Agent 映射、状态和结果入口，尚没有正式协调入口。
- 上游：SG-F01 提供 individual `TaskContract` 和下级 Agent 授权，SG-F05 提供 individual lifecycle 与 Session 底座，SG-F06 提供 individual `TaskResult`。
- 下游：SG-F07 只读诊断协调图、组状态、资源冲突和聚合结果，SG-F04 负责未来协调协议的版本兼容和真实发布验收。

SG-F08 必须作为独立大功能保留。SG-F01、SG-F05 和 SG-F06 分别解决单任务派发、单任务生命周期和单任务结果，不能单独表达多个任务之间的依赖、批次、共享资源、部分失败和 fan-in。反过来，SG-F08 只组合已有 individual 对象，不应重新拥有它们的生成、验收或平台执行。

### 4. 测试、fixture 与平台证据结论

当前已有证据能够证明：

- 多个进程并发写入同一 session 时，现有 StateStore 锁和原子更新可以保留 individual spawn 记录。
- `child_agents=allow` 会使 auto 选择 strict。
- individual spawn、Agent 映射、单目标平台错误、有限恢复、中断、Session 恢复和 individual result 具有定向测试。
- Skill 和运行边界明确要求父 Agent 使用原生工具并承担等待、恢复和验收责任。

当前证据不能证明：

- 批量 spawn 的部分成功、容量不足、幂等补派和不重复创建。
- 父子或孙级任务引用、授权传播和跨 session 恢复。
- 任务图拓扑、依赖循环、必需/可选节点或派发波次。
- 共享工作区的文件所有权、资源重叠、Git 冲突和安全串行化。
- 多目标等待任意一个、全部或依赖集合，以及 mailbox 首事件路由。
- 单 Agent 失败时其余分支继续运行、独立恢复和有限中断传播。
- individual results 的 fan-in、冲突保留、证据去重和组级状态计算。
- 真实 Codex 平台的并发槽位、嵌套 Agent 可见性、批量等待语义或父子关闭顺序。

未来测试应按协调计划、批次派发、父子传播、资源冲突、组状态、批量等待、部分失败和聚合结果八类建立独立矩阵；fixture 必须包含部分派发失败、网络断流、一个 Agent 恢复而其他 Agent 继续、compact/resume、迟到结果和嵌套任务。真实平台 smoke 与仓库单元测试必须分开记录。

### 5. 疑似无用、误导内容与退役边界

- `child_agents` 不是无用字段，应继续作为 individual contract 的授权信号；但它不能再被描述为已经表达父子任务图或规则传播。
- Skill 的批量派发表格不是无用内容，应保留用户透明度；但它只是展示格式，不能作为协调协议或运行状态证据。
- `tests/test_concurrency.py` 有效保护 SG-F05 的并发状态写入，不应删除；其宽泛文件名容易让人误以为覆盖多 Agent 业务协调，最终方案可考虑改名或增加明确模块说明。
- strict 对允许下级 Agent 和并发写入仍有用，但“提升到 strict”不能被描述为已经解决共享写冲突。
- SG-F07 的 `orchestration` 指导术语只能用于诊断导航，不能反向证明存在协调事件或协调运行时。
- 当前没有可以直接认定为 SG-F08 无用运行代码的内容，因为协调运行实现尚不存在；本轮主要发现的是现有单任务内容被过度解释的风险。
- 后台 scheduler、队列、远程协调服务、第二套 Agent API 和自动业务拆分器不进入目标架构，也不应在后续实现中新增。

### 6. 跨功能冲突与最终合并事项

1. **授权与关系混用**：SG-F01 的 `child_agents=allow|deny` 只能表达授权，SG-F08 需要独立 parent、child、depth 和 coordination 引用。
2. **单任务契约与协调计划混用**：TaskContract 应引用协调节点，而不是承载整张任务图、全部共享资源和聚合策略。
3. **扁平 StateStore 与组状态缺口**：SG-F05 当前只保存 tasks/agents；coordination、图版本、节点状态和 aggregate reference 必须明确分层及清理规则。
4. **状态语义重叠**：SG-F05 的执行/动作状态、SG-F06 的结果状态、SG-F08 的组状态和 SG-F07 的诊断问题不能继续共用一个扁平 `status` 枚举。
5. **等待规则粒度不一致**：现有 Skill 是单目标 20 分钟循环；SG-F08 需要等待集合和事件路由，但不能复制 SG-F05 的 individual 恢复状态机。
6. **strict 与资源安全混用**：strict 是证据和契约强度，不是文件租约、写入锁或无冲突证明。
7. **individual result 与 aggregate result 混用**：SG-F06 结果只能作为 SG-F08 汇聚输入；AggregateResult 应保存引用和组级结论，不复制所有正文。
8. **平台事实与仓库模型混用**：本地 Schema、fixture 和状态测试不能证明平台并发槽位、嵌套 Agent、mailbox 或批量等待保证。
9. **文档时点漂移**：主盘点仍只正式收录 SG-F01～SG-F03，SG-F05/SG-F06 已收口，SG-F07 仍只完成前 5 项；最终合并必须以各文档最新状态重新对账。
10. **历史测试数量漂移**：各文档记录的完整回归数量来自不同并行时点，最终方案只能引用验证命令和当次结果，不能把历史数量作为协议事实。

SG-F07 尚未完成输出、敏感信息和版本兼容三项，因此 SG-F08 对诊断字段、问题码和展示层的交接只确认职责方向，不提前冻结 SG-F07 的最终协议。

### 7. 最终统一修改包建议顺序

1. **统一身份与引用**：确定 task、execution、coordination、node、result、aggregate 和 event 的稳定 ID、版本、哈希及父子引用。
2. **建立协调计划**：新增静态 CoordinationPlan、节点、依赖、必需性、顺序和计划版本校验，由 AI 生成业务拆分，脚本维护机械字段。
3. **接入派发与资源边界**：在保持单次原生 spawn 的前提下记录批次、波次、容量、部分成功、shared resources 和 write scope。
4. **建立组状态与等待事件**：在 SG-F05 individual lifecycle 之上增加节点投影、批量等待选择、Session 恢复和有界事件记录。
5. **实现部分失败策略**：只恢复或中断受影响节点，按依赖传播暂停或待决策，不整批重派。
6. **实现结果汇聚**：消费 SG-F06 正式 TaskResult 引用，生成有版本和冲突记录的 AggregateResult，由父 Agent 完成业务裁决。
7. **接入诊断和版本兼容**：SG-F07 只读输出协调问题；SG-F04 验证 N/N-1 状态、结果和协调协议兼容及真实 Codex smoke。
8. **统一规则与测试资产**：最后同步 Skill、AGENTS、README、runtime boundaries、主盘点、Schema、fixture 和测试命名，删除已经退出兼容窗口的误导描述。

这些修改包具有明确依赖关系。不能先孤立扩展 TaskContract、给扁平 tasks 增加随意嵌套字段、把批量表格解析成运行协议，或只新增 coordination ID 而没有图版本、状态和结果引用。
