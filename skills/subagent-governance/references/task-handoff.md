# 任务交接与自主权边界

只交接会影响本次执行的设计、约束和验收依据。以下示例使用现有 TaskContract v2 字段；自然语言标签不构成新协议字段，也不要求每次全部填写。standard 的可选字段仍可省略，strict 的结构要求不变。

## 字段如何承载设计意图

| 字段 | 适合表达的内容 |
| --- | --- |
| `objective` | 唯一当前目标及预期业务结果 |
| `context.summary` | 必要背景、已确定的设计和影响选择的理由 |
| `scope` | 可修改的范围、可自主决定的细节；并行时的归属、接口与集成分工 |
| `forbidden_scope` | 必须保持的边界；需要先向父任务报告的越界条件 |
| `completion` | 可以观察和验证的完成条件，区分子任务交付与整体集成 |
| `evidence` | 实际检查及结果、未验证项；必要时的集成依赖 |

父任务将适用的信息写入契约，现有生成器会把非空内容传入派发正文。不要假定隔离上下文的子 Agent 已读父任务历史或本参考。程序可校验字段结构和声明材料，不能判断设计说明是否充分、方案是否正确或结果是否合格。

## 明确的小任务直接完成

反例：“修复问题，先给计划，等我确认每一步。”这会让已有明确目标的小任务产生不必要的往返。

改进示例：

```json
{
  "objective": "修复列表为空时汇总函数抛异常的问题",
  "scope": ["汇总函数及相关测试；沿用现有返回类型和错误模型，自主完成实现、必要验证及本次引入问题的修复"],
  "completion": ["空列表返回既定的零值，非空列表结果保持兼容；报告实际回归检查结果"]
}
```

这里完成条件已经包含需要的证据，不必为填满模板再重复到其他字段。

## 已定设计与可自主细节

反例：“实现游标分页，保持兼容，自行测试。”它没有说明兼容对象、分页语义或决策边界。

下例假设父任务已确定排序和兼容要求；实际任务应替换为自己的设计，不把此例中的选择视为通用分页规范。

```json
{
  "objective": "为订单列表增加可选游标分页",
  "context": {
    "summary": "已确定按 created_at、id 升序排列，以 id 区分相同时间戳；不传 cursor 时保持现有行为；沿用现有数据访问层和错误模型。"
  },
  "scope": [
    "订单查询实现及相关测试；辅助函数拆分和测试组织可自主决定",
    "完整完成实现、必要验证，并修复本次引入的问题"
  ],
  "forbidden_scope": [
    "不改变现有响应字段、权限过滤和错误格式",
    "若实现需要数据库迁移或改变既定排序语义，先向父任务报告原因与建议；继续不依赖该决定的工作"
  ],
  "completion": [
    "旧调用保持兼容；在固定数据集上连续翻页无重复、无遗漏，覆盖相同时间戳和空页",
    "无效游标遵循现有错误模型，分页保持现有权限过滤"
  ],
  "evidence": ["报告实际运行的检查及结果、未验证项和剩余问题"]
}
```

## 条件性的早期对齐

判断依据是未决问题是否会实质影响实现路线或突破既定边界，而非文件数量，也不是任务里出现了“数据库”或“鉴权”等词。已授权选择实现方案时，子 Agent 可自行取舍并交付；普通局部拆分、测试组织和本次引入问题的修复无需逐步请示。

如果关键设计尚未确定，尽早提出建议，避免在影响大量实现的假设上持续投入。最少说明：发现的事实、影响哪条约束、推荐方案及主要代价、需要父任务决定什么，以及哪些工作仍可继续。例如：

> 当前接口只返回数组，既定响应字段没有游标出口。建议先由父任务确定兼容的游标返回方式；改变响应对象会影响现有调用方。在接口决定前可继续查询层验证，无需改动共享响应类型。

未决设计不是新增的治理审批状态。普通方案沟通属于进行中的消息；确实无法继续交付、需要交还决定时，按现有终态义务报告结果、证据、剩余事项及所需决定。消息内容不自行建立平台终态，登记仍遵循 Skill 的证据与身份规则；不以一次对齐消息自动关闭任务，也不在终态后增加受管恢复路径。

父任务先判断是否已有授权作出决定，不能把每次子任务提问都转交用户。超出授权范围或需要用户作实质取舍时才向用户升级；继续其他不依赖该决定的已授权工作。这里不增加 Hook 拦截、审批状态机或统一停工机制。

## 并行修改的归属与集成

反例：让两个 Agent 同时“完善订单模块”，各自覆盖实现、共享类型和测试，却没有集成负责人。

有独立收益时才并行。只读探索可以按需安排；写入应按文件、目录或清晰职责分配，粒度足以识别重叠即可。共享接口要有明确维护者和当前约定；存在依赖时写清必要顺序，不默认各方可修改整个模块。

例如父任务维护共享响应类型，甲负责查询实现及单元测试，乙负责接口兼容测试；双方依据已确定的接口工作。给甲的契约可以是：

```json
{
  "objective": "实现订单分页查询层并交付给父任务集成",
  "context": {
    "summary": "查询接口及排序语义已由父任务确定；乙只修改接口兼容测试，父任务维护共享响应类型并负责最终接线与组合验证。"
  },
  "scope": ["订单查询实现及其单元测试；实现细节可自主决定；交付时说明接口依赖，父任务在甲乙交付后完成集成"],
  "forbidden_scope": ["不修改乙负责的接口兼容测试或共享响应类型；需要改变共享接口时向父任务报告"],
  "completion": ["查询层满足既定接口及排序语义，相关单元测试通过；明确尚待父任务执行的集成验证"],
  "evidence": ["实际修改范围、检查结果和集成依赖；不将子任务测试通过表述为整体集成通过"]
}
```

给乙的交接也应说明其归属、接口依据和集成责任，不能只在甲的契约中声明。父任务负责发现职责缺口、处理共享接口变更并验收组合行为；必要时安排先后修改。没有并行收益时由一个执行者完整交付。

`context.verified` 仅在 prepare 和 Pre claim 时校验声明材料。它不锁定文件，不保证执行期间材料不变，也不隔离共享工作区；任务分工同样不是文件锁或自动合并机制。
